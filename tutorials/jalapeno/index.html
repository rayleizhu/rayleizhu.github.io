Jalapeño：OpenAI 的第一颗自研芯片

一颗只做大模型推理、只给 OpenAI 自己用的 ASIC。本文先简要列出时间线和核心规格，再重点拆解它的架构，并逐项和 NVIDIA GPU 对照。最后单独讨论一个问题：OpenAI 据报在 GPT-6 Astra 中使用的 Looped Transformer（循环深度），是否和这颗芯片存在协同设计。

00一句话概览

Jalapeño 由 OpenAI 和博通联合开发，台积电 3nm 代工，2026 年 6 月 24 日发布。

做什么

只做 LLM 推理，不做训练，也不对外销售。目标是用比外购 GPU 更低的成本承接 ChatGPT、Codex 等产品的推理流量。

怎么做到

核心思路是尽量少搬数据：内存按 slice 划分、不维护全局硬件一致性、一颗芯片跑完推理的所有阶段。编程难度增加的部分交给 AI 写内核来补。

效果如何

自测每瓦吞吐是 GB200/GB300 的 1.5–1.9 倍，但还没有和同代 Vera Rubin 正面对比。2026 年底小规模部署，2027 年上量。

03架构详解：与 NVIDIA GPU 的六处不同

这一节是全文重点。每个小节先讲 NVIDIA GPU 的做法，再讲 Jalapeño 改了什么、代价是什么。

Richard Ho 在 Hot Chips 上提出的设计问题：如果一颗芯片的首要工作是服务现代和未来的语言模型，尤其是交互式 Agent，它应该长什么样？
  1. A1 出发点：推理的能耗和延迟主要花在搬数据上，而不是计算上。
  2. A2 片上结构：64 个 slice 各自直连本地 HBM，而 GPU 是所有 SM 共享 L2 和交织后的全部 HBM。
  3. A3 内存与编程模型：不提供全局地址空间和硬件一致性，由软件（主要是 AI 写的内核）显式管理数据放在哪。权重和 KV cache 常驻各切片本地的 HBM，跨单元传递的是激活值，而不是权重。
  4. A4 同构推理：一颗芯片跑完 prefill、draft、verify 等所有阶段，不拆成分离的机器池。
  5. A5 存储选型：用 HBM4 换容量，不走 Groq/Cerebras 的纯 SRAM 路线。
  6. A6 系统与互连：128 颗芯片组成本地域，用以太网扩展到 2,048 颗；不用 NVLink，主机用 x86。
A1出发点：能耗主要花在数据移动上读一次 DRAM 的能耗约是一次乘法的 170 倍
"能效归根结底是数据移动，以及数据移动的减少。" —— Richard Ho

这不是新观点。Horowitz 在 ISSCC 2014 给出过 45nm 工艺下各类操作的能耗：从片外 DRAM 读一个 32 位数，比做一次 32 位浮点乘法贵两个数量级以上。工艺进步后绝对值会变，但这个比例关系至今没有根本改变。

每次操作的能耗（45nm，对数刻度）

LLM 推理分两个阶段，瓶颈不同：

  • Prefill：一次处理完整个输入提示词，矩阵乘法很"胖"，受算力限制。
  • Decode：每生成一个 token，都要把激活的权重和 KV cache 从内存读一遍，受内存带宽限制。

判断一颗芯片适不适合 decode，可以看它的 屋顶线"脊点"，也就是算力 ÷ 带宽。脊点越低，越容易在不堆大 batch 的情况下把算力用满：

从表里能看出 Jalapeño 的取舍：单芯片算力并不领先，但它把带宽和算力的比例调到了更适合 decode 的位置，同时把功耗压到 700W。后面五个小节，都是围绕"让数据少走路"展开的。

两种结构的核心差别在于：一个计算单元要的数据，默认放在哪里？

为什么只固化"局部性"

Ho 从 TPU 带来的教训是：不要把一切写死在硅片里，也不要过拟合某一个模型。模型按周迭代，芯片要按年开发。因此 Jalapeño 唯一硬连线的决策是"内存和计算的就近绑定"，矩阵引擎、数据流、调度等其余部分都保持可编程。

slice 内部的矩阵引擎是权重驻留型脉动阵列（weight-stationary systolic array），和 Google TPU 属于同一架构家族。这一点 TechInsights 依据 Hot Chips 材料和 OpenAI 专利做了确认，2025 年的报道也早有提及。每个核心另有 SIMD 引擎和标量引擎，围绕高速本地内存排布。片上 SRAM 的容量至今没有公开。

A3内存与编程模型：去掉全局地址空间和硬件一致性省下功耗和延迟，代价是编程更难

A2 的物理结构直接决定了编程模型。GPU 给程序员的承诺是"一块大内存，随便访问"；Jalapeño 的承诺是"64 块小内存，你自己决定放什么"。

OpenAI 公布的证据包括：AI 用约 40 小时把 DeepSeek MLA 内核从理论上限的 0.31% 优化到 88.94%；首片回来后两个月内，把 GPT-OSS、DeepSeek R1、Kimi K2.5 三个模型调到了高性能。AI 不只用在软件上，芯片设计本身也大量使用了 AI，见 AI 辅助设计和 XLS 高层次综合。

文章认为，消除同步和数据移动开销后，HBM 不再是瓶颈：已发布测试中单用户速度达到 700–1,459 tokens/s，进入了以往 SRAM 型加速器的区间。

已知弱点：Ho 承认，在超长上下文场景下，分片内存方案可能遇到困难，因为 KV cache 会大到放不进一个 slice 的本地 bank。

权重放在哪：切片本地 HBM，而不是片上 SRAM

常听到的说法是"Jalapeño 让权重驻留本地"。更准确的说法是：模型权重和 KV cache 经过切分后，常驻在各个切片自己的 HBM 里。TechInsights 的原话是，每个核心切片对专属的 HBM 切片有低延迟的直接视图，"确保 KV 缓存和权重都保持高度局部化"。切片内的矩阵引擎是权重驻留型脉动阵列：一块权重载入阵列后固定不动，激活从阵列中流过。片上 SRAM 只做暂存，容量没有公开，也放不下前沿模型。Ho 的说法是："SRAM 带宽高，但容量太有限。"

需要说明的是，GPU 的权重同样常驻在 HBM 里，模型加载后就不再移动。两者真正的区别在于哪个计算单元读哪块内存：

维度NVIDIA GPUJalapeño
权重怎么存每个张量按地址交织，打散到全部 HBM 堆栈每个切片持有固定的一份分片，存在自己身边的 HBM 里
谁来计算任意 SM 都可能处理任意一段权重由持有这份分片的切片计算（owner computes）
读取路径HBM → 内存控制器 → crossbar → L2 → SM，必要时跨 die本地 HBM → 本切片
跨单元搬什么权重字节，量大激活值，量小
decode 一层时需要走片上网络的数据量（示意，对数刻度）

这相当于把 Groq、Cerebras 那种"权重钉在原地、让数据流过去"的空间式编程模型，从 SRAM 这一层搬到了 HBM 这一层：用 HBM 的容量保证放得下，同时保留"数据不远距离搬运"的好处。配套的编程模型是 Gluon，它把每个物理核心编程为一个持久线程块，并把完整的推理循环嵌进内核。

带来的好处

  • 省掉片上长距离传输的能耗：HBM 访问本身的能耗省不了，能省的是 crossbar、L2 查找、一致性维护，以及在光罩尺寸芯片上的长走线。
  • 带宽独占，时延可预测：每个切片平均约 240 GB/s 本地带宽（推算值），不和其他单元争抢，可以静态调度和精确预取，实际利用率更接近峰值。
  • 只搬激活，不搬权重：数据量相差约三个数量级。
  • 单用户低延迟靠横向扩展实现：一个 token 要读的权重分摊到多个切片乃至多颗芯片并行读取，每步时间约为 max（本地字节 ÷ 本地带宽）+ 集合通信时间。
  • KV cache 也在本地：这是 prefill 和 decode 能在同一颗芯片上完成的前提（见 A4）。

代价

  • 带宽仍是 HBM 级：每步还是要把激活的权重读一遍，单切片带宽只有几百 GB/s。
  • 负载必须均衡：每步耗时取决于最慢的那个切片。
  • MoE 有两难：专家固定在某些切片上，小 batch 时只有少数切片在工作；专家打散到多个切片，又会增加通信。GPU 的地址交织天然把带宽汇总在一起，没有这个问题。
  • 单切片容量会碎片化：每个切片约 3.4 GiB，长上下文的 KV cache 放不下时会溢出到别的切片。

A4同构推理：一颗芯片跑完所有阶段和行业主流的 prefill/decode 分离方案相反

目前 GPU 推理的主流做法是分离式部署：用一池 GPU 专门做 prefill，另一池专门做 decode，KV cache 再从前一池传到后一池。Jalapeño 反其道而行：prefill、投机解码的 draft 阶段和 verify/decode 全部在同一颗芯片上完成，各阶段专用模块可以电源门控，KV cache 不用搬动。

Ho 给出的理由是机队经济性：prefill 和 decode 的负载比例一直在变，而分离池的配比是提前几年就锁定的资本和电力投入。配比一旦不准，某个池就会空转，但照样消耗基础功耗。拖动下面的滑块试试：

A5存储选型：HBM4，不走纯 SRAM 路线在容量和带宽之间找平衡

专用推理芯片有两条典型路线。一条是 Groq、Cerebras 的纯 SRAM 路线：带宽极高，但单芯片容量小。另一条是 GPU 的 HBM 路线：容量大，带宽低一个到几个数量级。Jalapeño 选了 HBM，但把单位功耗下的带宽推得比 GPU 更高。

单芯片内存容量与带宽（对数坐标）

选 HBM 的理由：前沿模型的权重加上长上下文 KV cache，需要几百 GB 的容量。SRAM 容量受工艺限制，走 SRAM 路线就要很多芯片拼起来才能放下一个大模型。最终配置是 6 颗 12 层 HBM4，216 GiB，15.4 TB/s。

早期供应链消息说是"8 颗 HBM、双 die"，应以 Hot Chips 公布的数据为准。

04Looped Transformer：与芯片的协同设计？

2026 年 9 月有报道称，OpenAI 的 GPT-6 Astra 用到了"循环深度"（recurrent depth），也就是 Looped Transformer。同一家公司、同一年里，一边是"把权重钉在本地、尽量少搬数据"的芯片，一边是"同一组权重反复用"的模型。两者是协同设计的结果吗？本节从硬件机理、时间线和公开证据三方面展开讨论。

先说结论
  1. 第一代 Jalapeño 不太可能是"为 Looped 而设计"。它在 2025 年 2 月开始写 RTL、11 月流片，比 Astra 的报道早将近一年。公开基准测的全是非循环的开源模型，Astra 的生产推理跑在 Blackwell 上，Ho 的设计原则又恰恰是"不要过拟合某一种模型"。
  2. 但两者出自同一组第一性原理：减少数据移动、提高权重复用。Jalapeño 的几项设计（KV 本地化、同构推理、设备端持久循环）对循环模型天然友好，其中有的比对普通 Transformer 还要有利。
  3. Looped 的最大收益，取决于"共享块的活跃工作集能否驻留在片上"。片上 SRAM 容量至今没有公开，所以它是判断第二、三代是否会走向协同设计的关键观测点。如果能驻留，在高并发场景下 Jalapeño 相对 GPU 的优势反而可能缩小，原因见 L3、L4。

  • TechCrunch 两次强调：Astra 对这项技术的使用"据报道有限"，思维链预计仍然可读。
  • 首席科学家 Jakub Pachocki 在 X 上回应：包括 Astra 在内的前沿模型，计算图深度与 GPT-4 相差不到两倍。

对硬件分析来说，这意味着 Astra 至多是 SMELT 那种"部分层循环少数几次"的温和形态，而不是 Huginn 那种"小模型循环几十次"的极端形态。另外需要区分两种对照口径，它们对硬件的影响完全不同：

对照口径代表工作独立参数（存储量）每 token 计算量对芯片的主要影响
参数缩减："小模型想得更深"Huginn、Ouro减少，约为展开模型的 1/R与展开模型相同省容量
三项预算对齐SMELT不变，模型变窄后用更多专家补回相同不省容量；只有工作集驻留片上才省带宽
L2字节账本：循环模型每个 decode 步要读多少数据带宽收益只来自"驻留"

设 W 为每步激活的权重字节数（按与循环模型执行深度相同的展开模型计算），f 为参与循环的层占比，R 为循环次数，B 为并发序列数，K 为每条序列每步要读取的 KV cache 字节数：

展开模型： T = W + B·K 循环，工作集不驻留片上： T = (1−f)·W + f·W + B·K ← 每轮重读共享块，和展开模型一样 循环，工作集驻留片上： T = (1−f)·W + f·W/R + B·K ← 共享块只读一次，片上复用 R 轮 再加跨循环共享 KV： K → K·[(1−f) + f/R]

从这几个式子可以得出四个结论：

  1. 带宽收益只来自"驻留"。共享块如果只能放在 HBM 里，哪怕是 Jalapeño 的切片本地 HBM，每轮循环都要重读一遍。这时每步读取量和展开模型完全一样，循环只省下了存储容量。
  2. KV cache 不会随参数一起缩小。每一轮循环都有自己的 K/V，KV 总量和执行深度相同的展开模型一致。长上下文、大 batch 时 B·K 往往占大头，循环最多只能省掉 W 那一项，除非再做跨循环 KV 共享或压缩（Ouro、MoR、LoopVQ）。
  3. "把不同循环深度的 token 拼成一批"并不能提高复用率。这是一个常见误解：在循环次数统一的情况下，推进 B 个 token 各一整步仍要读 R 次共享块。这种拼批只在自适应深度时才有用，作用是填补提前退出留下的空位。
  4. 需要驻留的是"活跃工作集"，而不是整个共享块。在 MoE 中，一个 batch 只激活部分专家。SMELT 还发现，第二轮循环会复用第一轮所选专家的一个子集，重叠程度远高于随机。所以真正要放进片上的，是这一小部分活跃专家，门槛比"放下整个共享块"低得多。

情景预设

可以试试这几种操作：

  • 点"SMELT 式"：共享块的工作集放不下片上，循环对两种芯片的能效都没有影响，只有"参数缩减"口径下才会省出容量。
  • 点"小模型深思考"：工作集能驻留，又处在带宽受限区，两种芯片获得相同的能效增益，所以 Jalapeño 的相对优势不变。
  • 点"大 batch 吞吐 + 共享 KV"：驻留之后算术强度越过 Jalapeño 的脊点，Jalapeño 先撞上算力墙，GB300 却还能继续受益，Jalapeño 的相对优势因此缩小。
  • 点"长上下文 Agent"：B·K 占据绝大部分读取量，循环几乎不起作用；关键在于 KV 共享或压缩，以及容量。

L5时间线与证据芯片定型在前，模型传闻在后
两条时间线

支持"协同设计"的线索

  • Ho 强调 OpenAI 的优势在于全栈协同设计：研究人员和硬件团队可以直接在模型、软件与硬件之间做取舍。
  • OpenAI 称 Jalapeño"支持不断变化的模型架构"，并且是为"当前和未来的 LLM"设计的。
  • GPT-Astra 参与了 Jalapeño 的内核开发（和 Codex 一起生成 attention、MoE 内核），说明模型团队和芯片团队的工作流有交集。
  • 设计哲学高度一致："能效归根结底是数据移动"，而循环正是一种提高权重复用的模型侧手段。
  • OpenAI 内部研究可能早于公开论文。这一点无法证伪，但也无法证实。

不支持的线索

  • 时间线：RTL 始于 2025 年 2 月，流片于 2025 年 11 月；Astra 的报道出现在 2026 年 9 月。
  • Ho 的原则是"不要过拟合某一个模型"，唯一硬连线的决策是局部性。他也澄清过，自研芯片并不是为某个专属模型打造的。
  • 公开基准只测了 GPT-OSS、DeepSeek R1、Kimi K2.5，都不是循环模型。
  • Astra Ultrafast 的生产推理跑在 Blackwell 上，没有证据表明 Jalapeño 在服务 Astra。OpenAI 9 月 8 日把 Astra 和 Jalapeño 放在一起讲，也只谈经济性。
  • Astra 对循环的使用"有限"，深度不到 GPT-4 的两倍，循环不是它主导的负载特征。
L6三种假设与判断附观测清单

H1：第一代是为 Looped 专门设计的

证据强度：弱

和时间线、基准选择、Astra 的实际部署都对不上。唯一的支撑是"内部研究可能更早"，而这既无法证实也无法证伪。

H2：同一原理的两个产物

证据强度：中等偏强

芯片侧"少搬数据、只固化局部性"，模型侧"多复用权重"。两者因为相同的目标而相互兼容，但没有专门针对对方做优化。L4 中多数"有利"项也适用于普通 Transformer。

H3：第二、三代会和 Looped 协同

证据强度：合理，但没有直接证据

第二代预计几个月内流片，第三代在概念阶段。如果 OpenAI 认定循环是长期方向，第二、三代就是落地协同设计的窗口。

判断第二、三代是否走向协同设计的观测清单

  1. 片上 SRAM 是否披露，是否显著增大。这是循环带宽收益的开关。只要第二代 SRAM 或"本地域聚合 SRAM"明显增大，就是强信号。
  2. 是否增加算力相对带宽的配比，也就是提高脊点。如果负载因循环而变得更依赖算力，芯片会相应调整。
  3. 是否对跨循环 KV 做硬件支持，比如共享、压缩或向量量化解码（类似 LoopVQ）。
  4. 是否支持数据依赖的循环控制和提前退出，例如设备端调度器、动态 batch 重组。
  5. Astra 或后续循环模型是否部署在 Jalapeño 上，以及 OpenAI 是否公布循环模型的基准成绩。
  6. 第二代的 Hot Chips / ISSCC 论文里是否出现 recurrence、weight reuse across depth 之类的措辞。
一句话总结：第一代 Jalapeño 和 Looped Transformer 更像是"英雄所见略同"，不像是"量身定做"。循环让芯片省容量、省 KV 搬运，但要真正省带宽，前提是 SRAM 放得下共享块的工作集，而一旦放得下，Jalapeño 的带宽优势又会被削弱。如果 OpenAI 真要协同设计，最可能的方向是加大 SRAM 和算力配比，让下一代芯片更像 Cerebras。

风险与争议

  • 模型架构变化快于芯片迭代
  • 只供自用，设计成本摊销基础窄
  • 苹果商业秘密诉讼（主要涉及消费硬件）
  • "台积电入股"传闻不实
总体判断
  1. 工程上很亮眼。一家从没做过芯片的公司，第一代产品就拿到了有竞争力的推理能效。AI 辅助设计和写内核明显缩短了周期，这项能力可能比芯片本身更重要。
  2. 商业上还有待验证。领先有相当一部分来自 HBM4 对 HBM3e 的代差，和 Rubin 相比总成本大致持平。2027 年大规模上线后，单次推理成本能否稳定低于 GPU，才是真正的考验。
  3. 对 NVIDIA 的威胁不在单芯片性能。真正的变化是，最大的客户之一有了"够用"的替代方案，采购谈判时多了筹码。
